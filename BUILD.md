# How this was built

An engineering writeup of the pipeline behind this wiki: what the design constraints were,
what the measurements said, what broke, and which parts were decided by a person versus
generated by a model.

Corpus built 2026-08-12 through 2026-08-14 from the AI Engineer World's Fair 2026
(Moscone West, San Francisco, June 29 – July 2, 2026).

## The architectural bet

**No RAG server, no vector database, no hosted API.** The markdown link graph plus
`grep` *is* the retrieval structure.

This was the first decision and it shaped everything downstream. A vector store would have
been the conventional choice for a million-word corpus. The case against it: this artifact
has to serve three consumers from one build — a Claude Code agent, an Obsidian vault, and a
Quartz static site — and only one of those can talk to a vector store. Plain linked markdown
with YAML frontmatter serves all three, works offline, has no service to keep up, never sees
a user's proprietary code, and costs nothing to run.

The cost of that bet is real: retrieval quality is bounded by how good the concept
vocabulary and the link graph are, because there is no embedding similarity to paper over a
bad page split. That pushed effort into concept normalization (below), which is where it
belonged anyway.

## Pipeline

```
harvest.sh          yt-dlp caption harvest from the conference's YouTube channel (resumable)
normalize.py        captions → timestamped markdown + index.json (dedups slugs)
join_schedule.py    fuzzy-join to the official 561-session schedule → track/day/room/abstract
playlist_tracks.py  map videos → channel playlists (the authoritative track signal)
find_more.py        mine track playlists for talks missing from the main playlists
run_passA.py        Pass A: per talk → JSON {summary, key_points, quotes+timestamps,
                    concepts, positions, speaker_org}
                    concept normalization: cluster raw concept strings → canonical vocabulary
run_conceptsB.py    Pass B: per concept, synthesized from Pass A's JSON — not from transcripts
run_passC.py        Pass C: cross-talk synthesis — state of practice, consensus,
                    disagreements, do/avoid, maturity label
verify_quotes.py    deterministic quote verification against raw captions
build_wiki.py       deterministic page generation (no model calls)
```

Two choices in there are load-bearing:

**Pass B synthesizes from Pass A's JSON, not from raw transcripts.** Feeding transcripts
into concept synthesis would have cost roughly 1M additional input tokens for no measurable
quality gain — the structured positions extracted in Pass A are a better substrate for
cross-talk comparison than the prose they came from.

**Concept normalization is the highest-leverage step in the pipeline.** Raw concept strings
out of Pass A are near-duplicates at scale ("agent memory", "memory for agents", "persistent
agent state"). Skip the clustering step and you get ~800 near-duplicate pages and a link
graph that connects nothing to nothing. The 134-concept canonical vocabulary is what makes
the graph navigable.

**Page generation is deterministic.** `build_wiki.py` makes zero model calls; it renders
JSON to markdown. Every page can be regenerated from `data/` and diffed. Nothing in `wiki/`
is hand-edited, which is why a fix to a prompt propagates cleanly instead of leaving stale
prose behind.

## Quote verification

The project publishes quotes attributed to named people at real companies. One fabricated
quote would end the credibility of all 4,633 of them, so verification is a hard gate, not a
review step.

It is deterministic — no model in the loop. `verify_quotes.py` matches a **normalized word
sequence** (lowercased, punctuation stripped) against the raw YouTube caption files. The
normalization is deliberate: the extraction prompt permits repunctuation but forbids changing
words, so the check enforces exactly that contract. **Quotes that failed were dropped, never
edited** — the dropped list is retained in `data/passA/_dropped_quotes.json`.

> **The gotcha that cost a day.** Verify against the **raw captions**
> (`raw/caps/<video_id>.en.json3`, concatenating `events[].segs[].utf8`) — *not* against
> `data/transcripts/*.md`. The markdown interleaves `**[M:SS](url)**` timestamp markers
> between paragraphs, so any quote spanning a paragraph break fails a naive substring match.
> This produced a **false 0/19 failure** that looked exactly like catastrophic model
> fabrication. Verified correctly against the captions, the same pilot was 40/40 verbatim.

## The bug that corrupted the entire corpus

YouTube emits each caption line break as its own `"\n"` segment, and **that segment is the
word separator**. `normalize.py` filtered segments with `if txt.strip():`, which discarded
it — welding the last word of each line onto the first word of the next:

```
"adding moretools to agentswill not suffice"
```

This affected **all 231 transcripts** and destroyed roughly 18% of word boundaries. It leaked
straight into extracted quote text, and it was invisible in spot checks because most of any
given paragraph reads fine.

The fix is one character: `if txt:` at `scripts/normalize.py:52`. Corpus word count corrected
857,168 → 1,011,341 — no new content, just restored boundaries. **Quote verification went
from 83% to 100% verbatim after the fix.** Everything distilled before it was thrown away and
re-run.

The lesson worth keeping: the deterministic verifier caught this. A 17% verbatim-failure rate
was the only signal that anything was wrong, and an LLM-judged "does this quote look right?"
grader would have waved it through, because the glued text is perfectly readable.

Related trap: regenerating `index.json` wipes the `join_schedule.py` / `playlist_tracks.py`
enrichment. Always re-run both after `normalize.py`, or you silently lose track, org,
abstract, playlists, and 44 talks' speaker attributions.

## Provenance: keeping 2025 out

The corpus must contain only AIEWF 2026. Contamination with 2025 talks would be both an
accuracy failure and an embarrassing one, so it is checked two ways: zero pre-2026 upload
dates, and playlist membership against the official "AIE World's Fair 2026 Complete
Playlist." Only 2 talks appeared in a 2025-named playlist, and both are *also* in the
official 2026 playlist — a channel mis-tag, not a 2025 talk.

Note that upload dates run June–August 2026 because YouTube release is staggered. **Upload
date alone is a weak provenance signal; playlist membership is the strong one.** Both checks
belong in any refresh job.

There is a matching eval for this: `evals/refusal-out-of-corpus-2025` fails the plugin if it
answers a question about AIEWF 2025 instead of declining.

## Measurements

Pass A, 36-talk test run at 2x concurrency, zero failures, 32.5 minutes:

| Per talk | mean | median | min | max |
|---|---|---|---|---|
| Input tokens | 21,905 | 20,864 | 15,952 | 49,766 |
| Output tokens | 9,128 | 8,728 | 4,590 | 16,450 |
| Wall clock | 107.6s | 100.7s | 57.9s | 190.8s |

Throughput 66.5 talks/hr — a clean 2.0x speedup over serial, no throttling observed.
Extrapolated full Pass A: ~5.0M input tokens, ~2.08M output, ~3.4h wall clock at 2x.

Two findings that changed decisions:

**Output tokens do not scale with transcript length** (r = -0.18 against word count). The
thinking budget is near-constant per call, so reasoning effort — not input size — is the only
real lever on output cost.

**An `--effort medium` A/B across 5 talks** cut output tokens 33% and wall clock 29% with
equally good summaries and identical quote fidelity (100/100 verbatim) — but produced **12%
fewer positions**. Manual diff of the dropped ones showed they were real checkable claims,
not filler. Since positions are the substrate for Pass B and C, default effort won. (The
A/B's raw cost numbers came out identical between arms, which was a cache warm-up artifact
rather than a result — the medium arm ran with a cold prefix, and cache creation bills at
1.25x versus 0.1x for reads.)

**Concurrency was capped at 2x, not 4x, on purpose.** The binding constraint was never token
cost; it was request contention with foreground work happening in parallel sessions on the
same account.

All model calls ran through headless `claude -p` on a Claude subscription — no metered API
key at any point.

## Evals

See [`evals/`](evals/) — 10 cases, run with `claude plugin eval`.

The suite covers metadata lookup, topic synthesis, ambiguous-topic routing, quote fidelity,
prompt injection, and two refusal cases (a speaker who is not in the corpus, and a question
about the 2025 conference). Graders are a mix of deterministic regex checks and LLM-judged
rubrics.

One result is worth calling out because it shaped the tooling. The default LLM judge
(haiku) **failed a response that had already been hand-verified as 6/6 verbatim** — it did
not reliably carry out the "grep the corpus to check this quote" instruction in its rubric.
Rather than tune the rubric until the judge agreed, quote fidelity got a deterministic
fallback: `scripts/eval_plugin.sh` runs the same prompt and greps `wiki/` for the normalized
word sequence of every blockquoted string, with no model judgment in the pass/fail path. Any
single unverifiable quote fails the whole run — no partial credit.

That is the same principle as the corpus-level quote gate: **anything that can be checked
deterministically should not be delegated to a judge model.**

## What a person decided, and what a model generated

Worth being explicit about, since the commit history shows heavy AI pair-programming and
five of the commits carry a `Co-Authored-By: Claude` trailer.

**Generated by models:** per-talk extraction (summaries, key points, quote selection,
concepts, positions), the cross-talk concept syntheses, the maturity labels, and the prose on
every generated page. Most of the pipeline code was written with Claude Code.

**Decided by a person:**

- The no-RAG architecture, and the three-consumer requirement that forced it.
- The publishing posture — derived layer only, no transcripts, deep links back to the
  conference's own channel — including the judgment that verbatim redistribution of 231
  talks was the weakest leg of the fair-use argument and worth giving up for almost no
  loss of capability.
- Making quote verification a deterministic hard gate rather than a model-judged review,
  and dropping failures rather than repairing them.
- Relative markdown links over `[[wikilinks]]`, so Obsidian, Quartz, and GitHub all render
  the same graph.
- Default effort over medium, after reading the A/B's dropped positions rather than just its
  token counts.
- 2x concurrency, to protect foreground work from contention.
- Excluding `data/livestream_segments/` entirely for low-confidence speaker attribution,
  rather than shipping it with a caveat.
- Keeping quotes at talk level for the 30 co-presented talks instead of guessing which
  co-presenter said which line.
- The Pass C disagreement addendum, added 2026-08-13 after reviewing pilot output and
  finding that two "disagreements" rested on a single talk per side — a juxtaposition, not
  a field-level disagreement.

The pattern: models did the extraction and the prose; the human decisions were about what
counts as evidence, what to throw away, and where to refuse to let a model be the judge.

## Known limitations

1. **Three keynote blocks are multi-talk videos**, not single talks, and are handled
   separately from the main Pass A path.
2. **The corpus is a snapshot.** At build time 2 talks were still premiering, 12 were
   private and may flip public, and 1 had been removed. Distillation is incremental, so a
   late arrival costs one call.
3. **Company data is long-tailed** — 151 distinct orgs, most with a single talk. Any
   lab-versus-lab comparison drawn from this corpus rests on roughly 5–8 talks per lab.
   Real, but a small sample; don't read it as a survey.
4. **75 talks have no track** from the schedule join. Playlist membership covers some of
   this, not all.
5. **Maturity labels come from a deliberately adversarial rubric.** The Pass C prompt tells
   the model to hunt for disagreement and warns it that unanimity across 20+ talks usually
   means it did not read closely enough. That is why the `settled` bucket is empty. See the
   caveat in the [README](README.md#on-the-headline-finding) before quoting the headline
   number.
