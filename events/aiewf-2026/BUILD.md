# How this was built

An engineering writeup of the pipeline behind this wiki: what the design constraints were,
what the measurements said, what broke, and which parts were decided by a person versus
generated by a model.

Corpus built 2026-08-12 through 2026-08-14 from the AI Engineer World's Fair 2026
(Moscone West, San Francisco, June 29 to July 2, 2026).

## Scope, before anything else

The fair's official schedule listed 561 sessions: 412 sessions, 102 sponsor slots, 25
keynotes, and 22 workshops. This corpus covers the 246 talks that had been published to
the conference's YouTube channel as of the 2026-08-19 refresh (231 at the original build).
Talks were still premiering during the build, and 8 official-playlist videos remain private
and may go public later.

So this is a large sample of the fair, not a complete record of it. Every count in this
repo (246 talks, 134 concepts, 264 speakers, 4,925 quotes) describes that sample. Any
claim about "the conference" is really a claim about the published video subset, and any
topic that only came up in a workshop or an unpublished session is invisible here.

## The architectural bet

No RAG server, no vector database, no hosted API. The markdown link graph plus `grep` is
the retrieval structure.

This was the first decision and it shaped everything downstream. A vector store would have
been the conventional choice for a million-word corpus. The case against it: this artifact
has to serve three consumers from one build, a Claude Code agent, an Obsidian vault, and a
Quartz static site, and only one of those can talk to a vector store. Plain linked markdown
with YAML frontmatter serves all three, works offline, has no service to keep up, never
sees a user's proprietary code, and costs nothing to run.

The cost of that bet is real. Retrieval quality is bounded by how good the concept
vocabulary and the link graph are, because there is no embedding similarity to paper over a
bad page split. That pushed effort into concept normalization, which is where it belonged
anyway.

## Pipeline

```
harvest.sh          yt-dlp caption harvest from the conference's YouTube channel (resumable)
normalize.py        captions to timestamped markdown + index.json (dedups slugs)
join_schedule.py    fuzzy-join to the official 561-session schedule for track/day/room/abstract
playlist_tracks.py  map videos to channel playlists (the authoritative track signal)
find_more.py        mine track playlists for talks missing from the main playlists
run_passA.py        Pass A: per talk, produce JSON {summary, key_points, quotes+timestamps,
                    concepts, positions, speaker_org}
                    concept normalization: cluster raw concept strings into a canonical vocabulary
run_conceptsB.py    Pass B: per concept, synthesized from Pass A's JSON, not from transcripts
run_passC.py        Pass C: cross-talk synthesis. State of practice, consensus,
                    disagreements, do/avoid, maturity label
verify_quotes.py    deterministic quote verification against raw captions
build_wiki.py       deterministic page generation (no model calls)
```

Three choices in there are load-bearing.

**Pass B synthesizes from Pass A's JSON, not from raw transcripts.** Feeding transcripts
into concept synthesis would have cost roughly 1M additional input tokens for no measurable
quality gain. The structured positions extracted in Pass A are a better substrate for
cross-talk comparison than the prose they came from.

**Concept normalization is the highest-leverage step in the pipeline.** Raw concept strings
out of Pass A are near-duplicates at scale ("agent memory", "memory for agents", "persistent
agent state"). Skip the clustering step and you get roughly 800 near-duplicate pages and a
link graph that connects nothing to nothing. The 134-concept canonical vocabulary is what
makes the graph navigable.

**Page generation is deterministic.** `build_wiki.py` makes zero model calls. It renders
JSON to markdown. Every page can be regenerated from `data/` and diffed. Nothing in `wiki/`
is hand-edited, which is why a fix to a prompt propagates cleanly instead of leaving stale
prose behind.

## Quote verification

This project publishes quotes attributed to named people at real companies. One fabricated
quote would end the credibility of all 4,925 of them, so verification is a hard gate, not a
review step.

It is deterministic, with no model in the loop. `verify_quotes.py` matches a normalized
word sequence (lowercased, punctuation stripped) against the raw YouTube caption files. The
normalization is deliberate: the extraction prompt permits repunctuation but forbids
changing words, so the check enforces exactly that contract. Quotes that failed were
dropped, never edited. The dropped list is retained in `data/passA/_dropped_quotes.json`.

> **The gotcha that cost a day.** Verify against the raw captions
> (`raw/caps/<video_id>.en.json3`, concatenating `events[].segs[].utf8`), not against
> `data/transcripts/*.md`. The markdown interleaves `**[M:SS](url)**` timestamp markers
> between paragraphs, so any quote spanning a paragraph break fails a naive substring match.
> This produced a false 0/19 failure that looked exactly like catastrophic model
> fabrication. Verified correctly against the captions, the same pilot was 40/40 verbatim.

## The bug that corrupted the entire corpus

YouTube emits each caption line break as its own `"\n"` segment, and that segment is the
word separator. `normalize.py` filtered segments with `if txt.strip():`, which discarded
it, welding the last word of each line onto the first word of the next:

```
"adding moretools to agentswill not suffice"
```

This affected all 231 transcripts and destroyed roughly 18% of word boundaries. It leaked
straight into extracted quote text, and it was invisible in spot checks because most of any
given paragraph reads fine.

The fix is one character: `if txt:` at `scripts/normalize.py:52`. Corpus word count
corrected from 857,168 to 1,011,341, with no new content, just restored boundaries. Quote
verification went from 83% to 100% verbatim after the fix. Everything distilled before it
was thrown away and re-run.

The lesson worth keeping: the deterministic verifier caught this. A 17% verbatim-failure
rate was the only signal that anything was wrong, and an LLM-judged "does this quote look
right?" grader would have waved it through, because the glued text is perfectly readable.

Related trap: regenerating `index.json` wipes the `join_schedule.py` and
`playlist_tracks.py` enrichment. Always re-run both after `normalize.py`, or you silently
lose track, org, abstract, playlists, and 44 talks' speaker attributions.

## Provenance: keeping 2025 out

The corpus must contain only AIEWF 2026. Contamination with 2025 talks would be both an
accuracy failure and an embarrassing one, so it is checked two ways: zero pre-2026 upload
dates, and playlist membership against the official "AIE World's Fair 2026 Complete
Playlist." Only 2 talks appeared in a 2025-named playlist, and both are also in the
official 2026 playlist, so that is a channel mis-tag rather than a 2025 talk.

Note that upload dates run June through August 2026 because YouTube release is staggered.
Upload date alone is a weak provenance signal. Playlist membership is the strong one. Both
checks belong in any refresh job.

There is a matching eval for this: `evals/refusal-out-of-corpus-2025` fails the plugin if it
answers a question about AIEWF 2025 instead of declining.

## Measurements

Pass A, 36-talk test run at 2x concurrency, zero failures, 32.5 minutes:

| Per talk | mean | median | min | max |
|---|---|---|---|---|
| Input tokens | 21,905 | 20,864 | 15,952 | 49,766 |
| Output tokens | 9,128 | 8,728 | 4,590 | 16,450 |
| Wall clock | 107.6s | 100.7s | 57.9s | 190.8s |

Throughput was 66.5 talks/hr, a clean 2.0x speedup over serial, with no throttling
observed. Extrapolated full Pass A: roughly 5.0M input tokens, 2.08M output, and 3.4h wall
clock at 2x.

Two findings changed decisions.

**Output tokens do not scale with transcript length** (r = -0.18 against word count). The
thinking budget is near-constant per call, so reasoning effort, not input size, is the only
real lever on output cost.

**An `--effort medium` A/B across 5 talks** cut output tokens 33% and wall clock 29% with
equally good summaries and identical quote fidelity (100/100 verbatim), but produced 12%
fewer positions. A manual diff of the dropped ones showed they were real checkable claims,
not filler. Since positions are the substrate for Pass B and C, default effort won. The
A/B's raw cost numbers came out identical between arms, which was a cache warm-up artifact
rather than a result: the medium arm ran with a cold prefix, and cache creation bills at
1.25x versus 0.1x for reads.

**Concurrency was capped at 2x, not 4x, on purpose.** The binding constraint was never token
cost. It was request contention with foreground work happening in parallel sessions on the
same account.

All model calls ran through headless `claude -p` on a Claude subscription, with no metered
API key at any point.

## Evals

See [`evals/`](evals/). Ten cases, run with `python3 evals/run.py`.

The suite covers metadata lookup, topic synthesis, ambiguous-topic routing, quote fidelity,
prompt injection, and two refusal cases: a speaker who is not in the corpus, and a question
about the 2025 conference. Graders are a mix of deterministic regex checks and LLM-judged
rubrics.

One result is worth calling out because it shaped the tooling. The default LLM judge (haiku)
failed a response that had already been hand-verified as 6/6 verbatim. It did not reliably
carry out the "grep the corpus to check this quote" instruction in its own rubric. Rather
than tune the rubric until the judge agreed, quote fidelity got a deterministic fallback.
`scripts/eval_plugin.sh` runs the same prompt and greps `wiki/` for the normalized word
sequence of every blockquoted string, with no model judgment in the pass/fail path. Any
single unverifiable quote fails the whole run, with no partial credit.

That is the same principle as the corpus-level quote gate. Anything checkable
deterministically should not be delegated to a judge model.

## What a person decided, and what a model generated

Worth being explicit about, since the commit history shows heavy AI pair-programming and
several commits carry a `Co-Authored-By: Claude` trailer.

**Generated by models:** per-talk extraction (summaries, key points, quote selection,
concepts, positions), the cross-talk concept syntheses, the maturity labels, and the prose
on every generated page. Most of the pipeline code was written with Claude Code.

**Decided by a person:**

- The no-RAG architecture, and the three-consumer requirement that forced it.
- The publishing posture (derived layer only, no transcripts, deep links back to the
  conference's own channel), including the judgment that verbatim redistribution of 231
  talks was the weakest leg of the fair-use argument and worth giving up for almost no loss
  of capability.
- Making quote verification a deterministic hard gate rather than a model-judged review,
  and dropping failures rather than repairing them.
- Relative markdown links over `[[wikilinks]]`, so Obsidian, Quartz, and GitHub all render
  the same graph.
- Default effort over medium, after reading the A/B's dropped positions rather than just
  its token counts.
- 2x concurrency, to protect foreground work from contention.
- Excluding `data/livestream_segments/` entirely for low-confidence speaker attribution,
  rather than shipping it with a caveat.
- Keeping quotes at talk level for the 30 co-presented talks instead of guessing which
  co-presenter said which line.
- The Pass C disagreement addendum, added 2026-08-13 after reviewing pilot output and
  finding that two "disagreements" rested on a single talk per side, which is a
  juxtaposition rather than a field-level disagreement.

The pattern: models did the extraction and the prose. The human decisions were about what
counts as evidence, what to throw away, and where to refuse to let a model be the judge.

## Known limitations

1. **Coverage.** 246 of 561 scheduled sessions, limited to what the conference published as
   video. See the scope section above.
2. **Three keynote blocks are multi-talk videos**, not single talks, and are handled
   separately from the main Pass A path.
3. **The corpus is a snapshot.** At build time 2 talks were still premiering, 12 were
   private and may flip public, and 1 had been removed. Distillation is incremental, so a
   late arrival costs one call.
4. **Company data is long-tailed**, with 151 distinct orgs, most having a single talk. Any
   lab-versus-lab comparison drawn from this corpus rests on roughly 5 to 8 talks per lab.
   That is real, but it is a small sample, and it should not be read as a survey.
5. **72 talks have no track** from the schedule join. Playlist membership covers some of
   this, not all.
6. **Maturity labels come from a deliberately adversarial rubric.** The Pass C prompt tells
   the model to hunt for disagreement and warns it that unanimity across 20 or more talks
   usually means it did not read closely enough. That is probably why the settled bucket is
   empty. See the caveat in the [README](README.md#on-the-headline-finding) before quoting
   the headline number.

## Refresh 2026-08-19

Re-fetched the conference playlists and found 15 newly published talks, taking the corpus
from 231 to 246. Eight of them came from a playlist that did not exist at build time, the
new "Generative Media: AI Engineer World's Fair 2026" track. One further candidate turned
out to be a re-upload of an existing talk and was deduplicated by slug in `normalize.py`;
8 videos on the official playlists are still private. Both provenance gates were re-applied
to every new talk: zero pre-2026 upload dates, and membership in an official 2026 playlist.

Pass A ran on the 15 new talks, and quote verification was re-run across the whole corpus
with 100% verbatim retained (4,925 quotes, zero drops). The concept vocabulary did not
move: still 134 canonical concepts, with the new talks mapping onto existing ones rather
than forcing new vocabulary. 58 concepts gained talks and had their Pass C synthesis
regenerated. The playlist enrichment refresh also gave 4 previously untracked existing
talks a track and added 36 richer topic links.

The headline finding survived the refresh: still zero settled concepts, with the
distribution shifting from 87/43/4 to 80 consolidating, 50 contested, 4 frontier.

## Automating the refresh

That procedure is now a script, [`scripts/refresh_corpus.py`](scripts/refresh_corpus.py),
run weekly by a scheduled job. It does the same twelve steps in the same order, with
each one a hard gate: playlist discovery, provenance triage, caption harvest, normalize
plus schedule and playlist enrichment, Pass A, quote verification, concept assignment,
Pass C re-synthesis for concepts whose talk set moved, wiki and graph rebuild, count
sync, the eval suite, then commit and push. It exits nonzero on any gate failure and
pushes nothing. `--dry-run` reports discovery and triage without touching `data/`;
`--no-push` commits locally.

Four rules in it are worth stating, because each is a decision rather than an
implementation detail.

**Only official-2026-playlist membership auto-ingests.** The topical track playlists
are cross-year, and 2025 contamination is the failure this corpus most wants to avoid,
so a video that appears only in a topical playlist is triaged and reported for a human
rather than ingested. The "official" set is the two structural playlists plus any
playlist whose name contains "AI Engineer World's Fair 2026" — that pattern is what
caught the Generative Media track, which did not exist when the corpus was built.

**A week with nothing new touches nothing.** Triage runs before `normalize.py`, so a
no-op run leaves the working tree provably unchanged rather than rewriting `data/` with
identical content.

**The quote gate is a rate check, not a spot check.** More than 5% of a new talk's
quotes failing verbatim verification fails the run, because that is the signature of
the caption corruption described above rather than of normal model variation. The same
principle as the original gate: the deterministic verifier is the thing that caught it.

**Re-uploads are remembered.** A re-upload of a talk already in the corpus keeps its own
video id, and `normalize.py` keeps the fuller existing copy, so the re-upload's id never
reaches `index.json` — which makes it permanently eligible for ingestion and permanently
un-ingestable. Left alone it is re-accepted every week forever, and each run distills
nothing, finds zero new talks, and still commits and pushes the enrichment drift.
`raw/known_reuploads.json` records each one as it is detected, triage skips them before
spending a network call, and a run that ends up with no new talks reverts its own tracked
paths and exits before Pass A, Pass C, the eval suite, and git. Both guards have tests in
[`scripts/test_refresh_corpus.py`](scripts/test_refresh_corpus.py); `Q9ycQHbDdJs`, a
re-upload of `Fu45geO3zX8`, is the seed case.

**It updates counts, never claims.** The count-bearing files are edited by anchored
regexes that must each match exactly once, so a drifted file fails loudly instead of
being half-updated. If the maturity distribution ever produces a settled concept, the
run fails and says the "zero settled" headline needs a human rewrite. A cron job should
not be in the business of restating a finding.
